## Highest priorities

### 1. Prevent unrelated Stripe events from blocking collection

**Impact: high. Effort: small. Locally reproduced.**

The live adapter reads all Stripe event types, but its normalizer requires `data.object.id` before checking whether the event is supported. A normal `balance.available` object has no ID. It throws `provider_response_invalid`, preventing the whole page and its cursor from being committed, including valid payments on that page.

Evidence: [stripe.ts](../packages/adapters/src/monitoring/stripe.ts), lines 30–39 and 173–213; collection commit in [monitoring-jobs.ts](../packages/backend/src/monitoring-jobs.ts), lines 110–140. An injected balance event reproduced the exception.

Return no observations for unsupported types before validating type-specific fields. Optionally filter requested types to reduce traffic. Test a mixed unsupported-event/payment page and an authenticated unsupported webhook, retaining strict validation for supported events.

### 2. Fence every worker write, not only job completion

**Impact: high. Effort: medium. Database cases locally reproduced; analogous paths source-confirmed.**

The expanded monitoring page transaction checks job ownership. Legacy Supabase/Apple commits, metric cache writes and several error/health writes do not. Rejecting a stale worker at `finish` happens after these mutations.

Local PostgreSQL probes demonstrated a stale Supabase worker moving a newer cursor backward, an account response committing after disconnect, and an older metric result replacing the current cache while retained series correctly kept the newer value. A provider error before a fenced page commit can also overwrite another worker's health.

Evidence: [store-collection.ts](../packages/db/src/store-collection.ts), lines 20–113; [store-monitoring-series.ts](../packages/db/src/store-monitoring-series.ts), lines 16–22; [runner.ts](../packages/backend/src/runner.ts), lines 192–208. Core contracts currently omit the claim from these calls.

Extend the existing transaction/lease pattern to results and errors, checking active connection state inside the write transaction. Apply one freshness rule to the metric cache and retained series. Test replaced leases during successful collection, provider failure, disconnect and metric completion. Bound or split long provider work so it can complete within its lease.

### 3. Protect reconnects from older Supabase token refreshes

**Impact: high. Effort: small. Locally reproduced.**

A refresh started before reconnect can overwrite the freshly saved grant and clear a replacement refresh lease. `updateConnection` checks `active`, so plain disconnect is protected; an active reconnect is still vulnerable.

Evidence: [services.ts](../packages/backend/src/services.ts), lines 85–94. A fake token exchange that reconnected mid-request reproduced both stale credential replacement and lease clearing.

Reuse the ciphertext/lease comparisons already implemented by `replaceMonitorSecret` and `releaseMonitorRefresh` in [store-monitoring-lifecycle.ts](../packages/db/src/store-monitoring-lifecycle.ts), lines 24–46. Add reconnect, credential rotation and replacement-lease tests alongside the existing disconnect coverage.

### 4. Deliver reports that arrive after their scheduled date

**Impact: high. Effort: medium. Locally reproduced.**

Monitoring summaries only request yesterday. Google Play reports arrive 3–7 days late. When a result finally exists, the daily summary has moved to another date and never considers that result for notification. Eleven simulated daily runs with a three-day publication delay produced zero notifications.

Evidence: [monitoring-summary.ts](../packages/backend/src/monitoring-summary.ts), lines 11–14 and 32–48; publication delay in [google-play.ts](../packages/adapters/src/monitoring/google-play.ts), line 45.

Revisit a bounded set of eligible pending reporting dates, retaining the notification baseline and per-date deduplication. Test delayed availability, repeated runs, outage recovery and silent historical imports. Keep the provider's reporting date visible in the message.

### 5. Keep maintenance failure from stopping ordinary jobs

**Impact: high operational risk. Effort: small/medium. Control flow confirmed; write amplification reproduced.**

Node runs cleanup before consuming jobs. A cleanup failure leaves `lastCleanup` unchanged, so the worker retries cleanup every five seconds without reaching normal jobs. Cloudflare's hourly dispatch also awaits cleanup first.

Two database issues increase maintenance cost: monetary pruning rewrites every event older than 30 days even when its amount/currency are already null; expired-event cascades have no `monitor_observations.event_id` index. Two local cleanup calls physically rewrote the same already-pruned signup row. The missing index was confirmed in SQL, migration metadata and the database catalog. Production scale/latency was not measured.

Evidence: [apps/jobs/src/node.ts](../apps/jobs/src/node.ts), lines 17–24; [cloudflare.ts](../apps/jobs/src/cloudflare.ts), lines 17–21; [store-jobs.ts](../packages/db/src/store-jobs.ts), lines 145–166; [schema-monitoring.ts](../packages/db/src/schema-monitoring.ts), lines 78–89.

Isolate cleanup errors from collection/dispatch, update only monetary fields that are still populated, bound retention batches and add the foreign-key lookup index through an additive migration. Preserve stalled-cursor dedup retention. Test continued consumption after cleanup failure, repeated cleanup becoming a no-op, and bulk expiration with a representative query plan.

## Workflow and implementation order

1. **Restore collection guarantees:** unsupported Stripe events, Supabase refresh comparisons, complete result/error fencing and optional-match fallback. Put regression tests around these concrete races before changing implementation.
2. **Make reporting and delivery outcomes trustworthy:** delayed-date summary catch-up, unresolved send ambiguity, GA4/WorkOS quality signals and date/calendar handling.
3. **Remove avoidable operating limits:** isolate/bound cleanup, add its provenance index, then improve dispatch and ingestion round trips. Use representative synthetic workloads and oldest-job age, not speculative infrastructure.
4. **Improve operator feedback and frontend cost:** safe view editing, visible stale-data warnings, reconnect catalog invalidation, graceful shutdown, route splitting and adaptive report polling. Redact capability logging promptly as a small independent fix.

Add a small documented test-database bootstrap/preflight so a missing `TEST_DATABASE_URL` endpoint produces one actionable setup failure instead of dozens of downstream test failures. Keep it loopback/`_test` guarded and avoid modifying real installation credentials. The existing `pnpm check` is a useful baseline; broaden regression coverage around these demonstrated gaps rather than adding tests that mirror implementation.

Live provider acceptance remains a separate workstream. Existing `docs/status.md` contains dated deployment evidence and explicitly incomplete provider acceptance. This audit did not refresh that external state. Future acceptance should verify catalog access, pagination, a real supported report/event and observed message receipt separately, with authorized isolated accounts.

The architecture already has useful boundaries, transactional deduplication, guarded test fixtures and focused files. No reviewed maintained application source file exceeds the project's roughly 500-line guideline. Prioritize the behavioral gaps above over moving files or adding abstractions. The existing Authentication contract placement cleanup remains lower priority than these functional corrections.
