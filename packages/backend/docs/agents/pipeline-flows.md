# Collection and delivery flows

## Implemented today

Source: src/collectors.ts, runner.ts, services.ts and db stores.

| Flow                | Trigger / progression                                                                                                                                                                 | Retry / partial-failure behavior                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supabase accounts   | Source creation enqueues job; starts at source baseline; five-minute overlap unless catchup; 500/page, <=20 pages and 150s loop deadline; record events+cursor+fanout transactionally | Complete read schedules +5min; exhausted page/deadline budget +1s; anonymous IDs retained without fanout; late/deleted-between-polls accounts can be missed |
| Token refresh       | Access token expires within 60s; acquire 60s DB refresh lease, re-read current token, exchange and encrypt                                                                            | Ciphertext/lease compare-and-set prevents reconnect overwrite; release only the owned lease in finally; contention returns token_refresh_in_progress       |
| Apple collection    | One job per connection; reads previous seven UTC report dates; saves each date separately; repeat +1h                                                                                 | 404 stays pending; available absent app writes zero; changed totals increment revision; partial completed dates remain durable                             |
| Daily notifications | Project creation inserts job; checks every five minutes, capped at today's upcoming local dailyTime so a 23:59 window is not skipped; waits for enabled project                     | Newest missing date can fan out pending; late/corrected announced dates get revised keys; unannounced older history imports silently                       |
| Delivery            | Claim persisted delivery job; recheck destination verification/enabled, project enabled, destination link and active source                                                           | Cancel invalid routing; interrupted non-idempotent send uncertain; Resend same-key retry <=23h from first send, at most eight provider attempts            |

runOne claims through store, catches failures to stable codes, persists source/connection error, and reschedules recurring errors with bounded exponential backoff (up to one hour). Result and error writes require the current claim; job_lease_lost stops stale workers without overwriting newer health. A disconnected/missing connection terminates that job. Infrastructure Queue retries differ from application retries; normal runOne error handling returns after persisting failure. Delivery eligibility is a focused SQL read. Earlier ambiguous Resend outcomes stay uncertain if a later attempt is rejected, and the attempt cap is checked before sending as well as when scheduling retries.
No separate DAG engine, workflow orchestrator, raw-report archive or exactly-once external transaction exists.

Supabase account counts cover observations since the source connection baseline, not the customer's total account population or a historical signup import. `collectAccounts` excludes earlier rows, and only the newer monitoring-provider path creates independent history jobs. When comparing a newly connected Supabase source with upstream counts, use the same baseline and timezone; a zero observed count does not establish zero existing customers.

## Implemented today — monitoring flow

Credential/OAuth catalog probe → create source/state plus independent import/live jobs → lease-fenced page commits with fixed notification baseline → selected reports queued hourly with project-local 30/365-day ranges → provider-native results/retained daily points → configurable Overview. Completed auth and billing collectors schedule +5min; aggregate sources +1h; incomplete monitoring pages retain +3s continuation and completed history stops. The minute Cloudflare dispatcher adds up to a minute of scheduling delay; queue/rate limits may add more. Billing webhook authenticity precedes durable normalized inbox + processing job. Historical pages are silent. Native unique-user totals use period provider calls; daily summaries use visible views and preserve Apple correction handling. Per-connection budgets and Retry-After defer requests, and separate history/live errors describe partial failures.

Google Play uses the aggregate-source path and re-reads recent native report ranges for delayed data/corrections. Daily native-report summaries revisit the previous 14 project-calendar dates, exclude the source's notification-start date and earlier history, and skip already announced date/view keys. This covers ordinary 3–7-day publication delay; older outages remain visible in charts but do not trigger unlimited notification replay. Native provider date labels/timezones remain unchanged. Lemon Squeezy imports order/invoice pages silently, reconciles live pages, and receives authenticated billing webhooks. Slack/Discord verification deliveries may send while unverified; monitoring/test deliveries require verification. Codes expire in ten minutes; confirmation does not claim message read receipts.
